Procurator Nodus

Many applications.
One process.
Each kept apart.

A self-hosted substrate that runs all of your apps from one core, hands them sign-in, data, secrets, APIs and serving as shared capabilities, and never lets one app reach into another.

Watch on GitHub Pre-release

Nodus is Latin for knot. The tangle and the hub are the same points.

It can do that.

Everything below is in the first release. Short statements, no hedging. Each one is something you would otherwise assemble from three tools and a weekend. What comes after it is further down, under After the first release.

  1. Several apps. One process. Each one walled off.

    A shop, a blog, an internal tool and an API can share one server and one core, and still none of them can see another's data, sign-ins or secrets. Isolation is how the system is built, not a setting you remember to turn on.

  2. One account signs in to every app in a group.

    Put related apps in an app group and a person signs up once: same password, same second factor, one place to reset it. What that account may do is still decided app by app, and apps in other groups never learn the account exists.

  3. Several organisations. One install.

    Groups are how one install hosts things that must not know about each other: separate companies, departments or brands. Each group has its own sign-in realm and its own users, roles decided per app, and its own data. Nothing crosses a group line unless both sides declare it, or one app calls another's API with an API key scoped to exactly that.

  4. A static site, a single-page app and a service written in anything, side by side. HTTPS included.

    Serve static files, route a single-page app, run a server-rendered app such as Next.js or Astro, or stand a service in another language behind the built-in proxy. On the open web, certificates are issued and renewed for you. One place to configure all of it.

  5. Start an app in one command.

    Pick a starter: a notes app in React for many users, a blog with one author, a static site, or an API-only app. It lands in your own folder, and the notes and blog starters arrive with sign-in pages, a database and the SDK already wired to your install. Change the pages, build, and pn deploy puts it live.

  6. Files, mail and scheduled jobs, without another service.

    Each app gets its own file storage on the server, private or public, and it travels in your backups. Apps send mail through the relay you already use, and a message that cannot go out yet is retried rather than lost. An app can schedule its own recurring jobs, and a long-running worker can run beside it as a service.

  7. One data model, assembled from several places.

    Declare a model whose parts live in different stores: a row in Postgres, documents in MongoDB, a live field from someone else's HTTP API. Ask for one record and get one object back, already joined. Your code never learns which store held which piece.

  8. Ask once. Every source answers.

    A federated query fans out to several stores at the same time, feeds the result of one into the filter of the next, and returns a single answer that names which parts came back and which did not. The stores can be SQLite, Postgres, MySQL or MariaDB, SQL Server, MongoDB, or a plain HTTP API.

  9. Two ways in to your data. Pick the one that fits the query.

    The model API for everyday calls: filter, sort, page and follow relationships. Raw SQL or MongoDB queries for the hard ones: joins, window functions, each database's own features, on Postgres, MySQL, MariaDB, SQL Server and MongoDB. A raw query lists the database and the tables or collections it touches, and PN checks it against that list and the app's permissions before it runs.

  10. Turn an app into an API in four commands.

    Scaffold it, add an endpoint, deploy, mint a key. No server to write, and the endpoint's code can use Node's built-ins and the npm packages you declare. Before anything goes live, the deploy tells you in plain words what the API will be allowed to do. The endpoint answers over REST and through both SDKs, behind keys you issue and can revoke.

  11. Secrets stay out of your code. Outbound calls go only where you said they would.

    An API names the secrets it needs and the hosts it will talk to, and that is the whole declaration. The value of a secret never appears in your repository. A call to a host you did not list is refused before it leaves.

  12. Two SDKs, one contract.

    TypeScript and Python, kept in step by tests that check both, so a capability in one is a capability in the other. The TypeScript SDK adds React hooks for sign-in, queries, changes, paging, permissions and file uploads.

  13. Install it. Answer the wizard. It is a service.

    The setup wizard writes the configuration and registers PN as a system service. The first start prints the link to the admin console, where you watch health and do light setup. The pn command does everything else, and pn status and pn doctor tell you what is running and what is wrong.

  14. On one machine, on your own network, or on the open web.

    Install PN for the machine it runs on, for a home or office network, or for public sites. On one machine it answers only that machine, so terminal tools and background jobs can use it with no certificate at all. On a private network it serves over HTTPS with a certificate you provide, to the addresses you allow. On the open web it obtains and renews public certificates itself. Start small and move it out when you are ready.

  15. Patch it with one command. If it does not come up healthy, it puts itself back.

    pn update stages the new release, snapshots the old one, switches over and checks health. If the new release does not come up healthy, the one that was working is put back without waiting for you. pn rollback does the same on request.

  16. Backups you can carry off the server.

    pn backup writes one sealed file, encrypted and signed, meant to leave the machine. pn restore puts it back on the same server or a fresh one, checks the whole file before writing anything, and signs everyone out so no sign-in from before the restore stays valid. Scheduled snapshots stay on the host for the quick cases. Database servers such as Postgres are backed up with their own tools, and their dumps can be sealed into the same file.

  17. No telemetry. Your users can take their data with them, or erase it.

    PN does not report how you or your apps use it: no analytics helper, no usage statistics, no crash reports. Once a day it checks for a newer release and tells you; it never installs anything on its own, and you can turn the check off. Export and erasure are capabilities every app inherits, so the people using what you build keep rights over their own data without you writing a line.

Every error has a code, and every code has a fix

There are 800+ error codes, and counting.

Each one starts with the part of PN that raised it, such as SERVE or DATA, and keeps its meaning. See one in a log or an API response and one command tells you what caused it, how to fix it, its category and HTTP status, and a hint. The SDKs return the same codes, so an app can handle an error by name instead of parsing its message. When all you have is a phrase from the message, pn errors find turns up the code.

How it holds together

At the center is the core. It is the one thing you install, and its job is to keep apps apart while letting them share what you choose.

Around it sit spokes. Each provides one capability: sign-in, data, files, mail, secrets, serving, APIs, the admin console. An app uses the spokes it needs, and every request between parts passes through the core, so a spoke never reaches another spoke directly and an app never reaches another app.

You install one package and run a command-line setup. From then on the pn command does the work and the admin console shows you the state of it all. The capabilities come with the install. Adding an app is a declaration and a deploy.

Hammer stands apart

Prime directive: Protect the system and its users’ data. Nothing outranks it.

Hammer is the overwatch. It runs as its own process beside PN, not inside it, so a failure in the system it guards cannot take the guard down with it. In production, PN does not run without it.

It keeps its own sealed store, separate from PN's, that no app can reach. It keeps the record of what happened in a form where tampering shows. And it watches security signals, not your users: it does not know what they read, only when something in the system starts to behave like a threat.

Ordinary trouble does not set it off. What PN refuses on its own is recorded and reported, and a database outage never takes your sites down: at most, writes pause while the console stays up. When PN itself goes wrong, Hammer does not negotiate. It stops PN, the service comes back clean, and you are told.

What it replaces

The services you would otherwise stitch together, each with its own account, config and failure mode, become one install that you update, back up and watch as one thing.

  • A sign-in and user-management serviceAccounts, sign-in, password reset, second factor and roles, per app, shared across a group when you say so.
  • An API gateway with key managementEndpoints declared once, answered over REST and through the SDKs, behind API keys you mint and revoke, with rate limits per app and per endpoint.
  • A database access layerOne model API across SQL and document stores, plus HTTP APIs as data sources, and raw queries checked against what they declare.
  • File storage, a mail queue and a job schedulerFiles for each app, private or public, outgoing mail that is retried rather than lost, and jobs each app schedules for itself.
  • A secret storeSecrets declared by name and handed only where they were declared. The values never sit in your code.
  • A reverse proxy and certificate renewalStatic sites, single-page apps, server-rendered apps and proxied services on one listener, with HTTPS issued and renewed for you.
  • Deploy, update and backup scriptsOne install, one update command that puts the old release back if the new one fails to come up, sealed backups of everything PN holds, restorable onto a fresh server.
  • Monitoring and an audit trailHealth in the admin console and from the terminal, and a record of what happened, kept by Hammer where tampering shows.

A whole company, built as the proving ground

Imaginary Grocery Company is a fictional grocery and logistics business built on PN as a complete reference stack: two groups on one install, with every declaration, model, view and seed file written out. It is the stack PN is proven against before release. At release it goes live here as a working demo with test logins you can try. Publishing its source as a repository you can read, run and borrow from comes after the first release. The apps are not full products; they are complete enough to show what a finished stack looks like.

  • Inside the companyAn employee portal, stock operations, transport dispatch, a yard board and HR admin. One employee account across all of them, with a different role in each app, and each app keeping its own sign-in.
  • Facing the publicA customer storefront in its own group with its own customer accounts: catalog, availability, cart, checkout, orders. An employee who shops there is a customer there, nothing more.
  • Data from three placesRows in Postgres, documents in MongoDB and a live weather API, combined into dashboards and boards for the portal, the stock desk, dispatch, the yard and the storefront.
  • Across the lineThe storefront learns what is in stock through an API that stock operations exposes behind a scoped API key. The two groups never share a database.

This release already carries the shape of a real organisation, its internal tools and its public sites on one platform, and PN is being built to go further in that direction.

Who it's for

From a single box to an organisation with departments and a public face. The scale changes; the shape of the install does not.

The box in the closet

A Linux home lab or office server running several tools, on one machine or across your own network. One sign-in for all of them, each tool kept apart from the rest, encrypted connections with your own certificate, updates that put themselves back if they fail, and a backup you can carry to the next box.

The organisation

Internal tools for staff in one group, customer sites in another, more groups for other departments or brands as they come. Staff sign in once with a different role in each tool, customers have their own accounts, partners get API keys, and no group can reach into another. The example above is this shape.

The developer with an API

Four commands from API to endpoint to deploy to key. The endpoint answers over REST and through the TypeScript or Python SDK, its code can use the packages you declare, and every error carries a code the caller can act on. Already run an MCP server? Put it behind PN's proxy and let it use PN through the SDK.

After the first release

The first release is the foundation. Much of what comes next is already built and is being finished; the rest is planned. No dates: each addition arrives when it works the whole way through, and the order follows what people actually need.

  1. Built, being finished

    • NodusQL: one text query language that PN translates for every supported store
    • More kinds of federated read, and saved queries you can reuse
    • Redis as a data source, and vector search with Qdrant
    • GitHub and Google sign-in
    • Astro server helpers
    • A small set of built-in text, formatting and cryptographic helpers

  2. In the updates after that

    • Named SQL statements with bound values that only return each caller's own rows
    • WebSocket connections for apps behind PN
    • PN's own MCP support, once it is proven against real clients; until then, run your own MCP server behind PN's proxy
    • Sharing a specific private file or secret between two apps, with permission you can revoke
    • Certificates verified through DNS, including wildcard certificates
    • Fuller console screens: privacy requests, audit and alert history, and an undo window for deleted apps
    • Public sites and network-only apps on the same install
    • Installing and updating machines with no internet connection
    • More starters, generated API descriptions, and endpoints written in TypeScript
    • The example company's source as a public repository, and more public examples

  3. Further ahead

    • Extensions from other developers, signed and reviewed, and a marketplace to find them
    • Transactions within one database, and writes across several data stores
    • A certificate authority PN runs for your own network
    • Rate limits per role, and usage metering
    • One-click installs with hosting providers
    • Selected core components and Hammer rewritten in Rust, where it measurably helps
    • Horizontal scale-out: capabilities and apps sharded across several servers on one network
    • Multi-region federation: independent PN instances in different regions working together as one system
    • More platforms: more Linux distributions, native macOS, and a look at native Windows

What will not change

  • Free and open source, under the Apache-2.0 license
  • No telemetry: PN never reports how you or your apps use it
  • Your apps and your data stay on your server
  • Every app kept apart from every other, by design
