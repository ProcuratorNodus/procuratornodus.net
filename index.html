Procurator Nodus

Many applications.
One process.
Each kept apart.

A self-hosted substrate that runs all of your applications from one core, hands them identity, data, secrets, APIs and serving as shared capabilities, and never lets one application reach into another.

Watch on GitHub Pre-release

Nodus is Latin for knot. The tangle and the hub are the same points.

It can do that.

Everything below is in the release we are building now. Short statements, no hedging. Each one is something you would otherwise assemble from three tools and a weekend.

  1. Several applications. One process. Each one walled off.

    A shop, a blog, an internal tool and an API can share one server and one core, and still none of them can see another's data, sessions or secrets. Isolation is how the system is built, not a setting you remember to turn on.

  2. One account signs in to every app in a group.

    Put related apps in a group and a person signs up once: same password, same second factor, one place to reset it. What that account may do is still decided app by app, and apps in other groups never learn the account exists.

  3. A static site, a single-page app and a service written in anything, side by side. HTTPS included.

    Serve static files, route a single-page app, or stand a process in another language behind the built-in proxy. Certificates are issued and renewed for you. One place to configure all of it.

  4. One data model, assembled from several places.

    Declare a model whose parts live in different stores: a row in Postgres, documents in MongoDB, a live field from someone else's HTTP API. Ask for one record and get one object back, already joined. Your code never learns which store held which piece.

  5. Ask once. Every source answers.

    A federated query fans out to several stores at the same time, feeds the result of one into the filter of the next, and returns a single answer that names which parts came back and which did not. The stores can be SQLite, Postgres, MySQL or MariaDB, SQL Server, MongoDB, Redis, Qdrant, or a plain HTTP API.

  6. NodusQL. One query language for all of them.

    Write a statement once and PN turns it into the right form for the store underneath, whether that is a SQL table, a document collection or a vector index. Fields, operators, ordering and limits read the same everywhere. Name a store directly with FROM mongo_orders.orders when you want to.

  7. Turn an app into an API in four commands.

    Scaffold it, add an endpoint, deploy, mint a key. No server to write. The same endpoint answers over REST, through the SDK, and as a tool to AI assistants over MCP, each behind a key you issued and can revoke.

  8. Secrets stay out of your code. Outbound calls go only where you said they would.

    An API names the secrets it needs and the hosts it will talk to, and that is the whole declaration. The value of a secret never appears in your repository. A call to a host you did not list is refused before it leaves.

  9. Install it. Answer the wizard. It is a service.

    The setup wizard writes the configuration and registers PN as a system service. The first start prints the link to the admin console, where you add capabilities, configure them and watch health. From the terminal, pn status and pn doctor tell you the same story.

  10. Patch it with one command. If it does not come up healthy, it puts itself back.

    pn update stages the new release, snapshots the old one, switches over and checks health. A failed check rolls the instance back to the release that was working, without waiting for you. pn rollback does the same on request.

  11. Nothing phones home. Your users can take their data with them, or erase it.

    There is no analytics helper, no page-view call, nothing that reports back out of the box. Export and erasure are capabilities every application inherits, so the people using what you build keep rights over their own data without you writing a line.

How it holds together

At the center is the core. It is the one thing you install, and its job is to keep applications apart while letting them share what you choose.

Around it sit spokes. Each provides one capability: sign-in, data, secrets, serving, APIs, the admin console. An application uses the spokes it needs, and every request between parts passes through the core, so a spoke never reaches another spoke directly and an app never reaches another app.

You install one package, run a command-line setup, then manage the rest from the admin console. Adding a capability is an install. Adding an application is a declaration.
